Bối cảnh: LLM viết test rất nhanh, nhưng chưa đáng tin

Rủi ro 1: không chạy được

Sai cú pháp, sai import, gọi hàm sai cách. Test như vậy không kiểm tra được gì.

Rủi ro 2: bỏ sót

Không đi qua một số nhánh, thiếu trường hợp biên. Lỗi nằm ở đó không bị phát hiện.

Rủi ro 3: viết sai

Sai giá trị mong đợi. Nguy hiểm nhất là test viết theo code đang sai, làm bug bị giấu đi.

Vấn đề của đề tài: làm sao để test do LLM viết chạy được, đủ chặt, và không che giấu bug trong code?

Ví dụ xuyên suốt: một bug chỉ do thiếu một dấu bằng

Hàm đổi điểm số sang điểm chữ

def letter_grade(score): """80 <= score < 90 -> "B" 65 <= score < 80 -> "C" ...""" if score >= 90: return "A" elif score > 80: # đặc tả: >= 80 return "B" elif score >= 65: return "C" ...
Đầu vàoĐặc tả yêu cầuCode trả về
85BBĐúng
80BCSai
79CCĐúng

Nếu LLM đọc code rồi viết test theo code

assert letter_grade(80) == "C"

Test này pass. Người xem thấy test xanh nên tưởng code đúng, còn bug thì bị giấu đi. Em gọi hiện tượng này là hợp thức hoá bug.

Thước đo 1: coverage cao chưa chắc bắt được lỗi

Khái niệm

  • Unit test: đoạn kiểm tra tự động cho một hàm, đưa đầu vào rồi so kết quả với giá trị mong đợi
  • Line coverage: tỉ lệ dòng code mà test đã chạy qua
  • Branch coverage: tỉ lệ nhánh if/else mà test đã đi qua

Vì sao chưa đủ: thử với ví dụ của đề tài

assert letter_grade(85) == "B"
  • Test pass, nhánh "B" được tính là đã phủ
  • Bug ở mốc 80 vẫn còn nguyên, vì test không thử đúng giá trị biên

Bằng chứng từ nghiên cứu

  • Inozemtseva và Holmes, ICSE 2014: 31.000 bộ test trên 5 hệ thống Java. Khi cố định số lượng test, coverage chỉ tương quan thấp đến vừa với hiệu quả của bộ test
  • MutGen (Wang và cộng sự): nêu ví dụ bộ test đạt 100 % coverage nhưng chỉ đạt 4 % mutation score
Coverage cho biết code đã được chạy qua, không cho biết kết quả có được kiểm tra đúng hay không.

Mỗi mutant còn sống cho biết chính xác bộ test đang bỏ sót điều gì. Đây là thông tin đề tài đưa lại cho LLM.

Vì sao tin được thước đo này

Just và cộng sự, FSE 2014: trên 357 lỗi thật của 5 ứng dụng, khả năng phát hiện mutant tương quan có ý nghĩa thống kê với khả năng phát hiện lỗi thật, độc lập với coverage.

Oracle problem

Khó biết kết quả nào mới là kết quả đúng. Theo khảo sát của Barr và cộng sự (IEEE TSE, 2015), con người vẫn là nguồn xác nhận cuối cùng.

Cách đề tài tiếp cận

Dùng docstring làm căn cứ để so sánh. Chương trình chỉ gắn nhãn nghi có bug, người kiểm tra mới là người xác nhận. Đề tài không tuyên bố giải quyết xong bài toán này.

Vấn đề bài báo đặt ra

Test do LLM viết thường chỉ được đánh giá bằng coverage, mà coverage liên quan yếu đến khả năng phát hiện lỗi. Test còn hay sai cú pháp, sai giá trị mong đợi và bỏ sót trường hợp biên.

Ý tưởng chính

Đưa mutant còn sống vào prompt để LLM viết đúng test còn thiếu. Prompt gồm bộ test hiện tại, một mutant còn sống và câu:

"Test này không phát hiện được lỗi trong đoạn code sau"

Quy trình 6 bước của MuTAP

1Sinh testĐưa code cho LLM, hỏi kiểu zero-shot hoặc few-shot
2Sửa cú phápCó lỗi thì yêu cầu LLM sửa, tối đa 10 lần, không gửi kèm thông báo lỗi
3Sửa giá trị mong đợiGiá trị LLM viết khác kết quả của code thì thay bằng kết quả của code
4Đo mutationDùng MutPy tạo mutant, chạy bộ test, tính mutation score
5Bổ sung promptChưa đạt 100 % thì thêm một mutant còn sống vào prompt để LLM viết thêm test
6Rút gọn bộ testChỉ giữ test làm tăng điểm, dùng thuật toán tham lam
Bước 3 giả định code luôn đúng. Em sẽ quay lại điểm này ở trang 14.
Bước 4 và 5 lặp lại đến khi đạt 100 % hoặc dùng hết mutant còn sống. Đây là đóng góp chính.
Bước 2 và 3 cũng là phần tác giả nhấn mạnh: LLM cần xử lý sau mới cho test tốt.

Quy tắc đầu tiên trong mọi prompt

"Viết assert theo ĐẶC TẢ trong docstring, KHÔNG suy ra kết quả mong đợi từ cách code cài đặt."

Chỉ chọn SUSPECTED_BUG khi đặc tả nói rõ hành vi mong đợi và code vi phạm điều đó.

Một mutant thật đã đưa vào prompt

Mutant #16, dòng 43: raise ConfigError("Key rỗng") -> raise ConfigError("XXKey rỗngXX")

Với loại mutant này, LLM viết test kiểm tra cả nội dung thông báo lỗi.

Log thật: hai test fail, hai cách xử lý

SUSPECTED_BUG: nghi code có bug

# test_letter_grade_B letter_grade(80) == "B"

LLM trả lời:

"Docstring defines 80 <= score < 90 as 'B', but code returns 'C' for score=80 due to using >80 instead of >=80."

Xử lý Giữ test, gắn nhãn, báo cho người kiểm tra

TEST_WRONG: test viết sai

# test_final_score_rounding final_score(...) == 44.9 -> 48.1

LLM trả lời:

"Second assert expects 44.9, but per docstring the correct rounded result is 48.1."

Xử lý Sửa giá trị mong đợi trong test

Vòng 0: 18 pass, 2 fail
Vòng 1: 19 pass, 0 fail, 1 test mang nhãn nghi bug
Nếu dùng bước 3 của MuTAP, test ở bên trái sẽ bị đổi thành == "C" và bug ở mốc 80 bị che đi.

  • nemotron-3-super-120b miễn phí, 50 request/ngày

Cách chấm

Mutation held-out: bỏ các mutant đã đưa vào prompt của C và D, rồi dùng chung tập còn lại để chấm cả bốn cấu hình.

Tập held-out để chấm
Đã lộ

Phát hiện bug: có test fail hoặc mang nhãn trên code lỗi, và pass trên bản đã sửa. Vì vậy nhãn đúng hay sai được chấm tự động.

Tách hai bước: bước sinh gọi LLM và ghi log; bước chấm chạy lại từ log, không tốn API.

Sửa sai của chính em: lúc đầu em chấm trên tập có lẫn mutant đã lộ; một lượt review độc lập phát hiện lỗi này, sửa xong kết luận thay đổi.

Cần nói rõ

Ở A, test cũng đã fail ở cả hai bug, nhưng không được phân loại nên người dùng phải tự đoán nguyên nhân.

Chưa thấy tác dụng

Coverage đạt 99 % ngay từ lần sinh đầu, nên phản hồi coverage chưa thể hiện được trên các module nhỏ này.

Đổi lại, số lần gọi LLM tăng từ 1 lên 2,4 đến 3,2 lần mỗi module. Đây là quan sát ban đầu: 5 module, 1 lượt, chưa có ý nghĩa thống kê.

Tính cả mutant đã đưa cho LLM: 83,0 lên 86,0 %, tăng 3 điểm. Phản hồi mutation trông có tác dụng.

91,8 % trước và sau, không tăng. Chưa thấy khả năng bắt lỗi mới tốt lên.

Vì sao điểm held-out cao hơn?

Mutant khó nhất còn sống nên được đưa vào prompt, và vì thế bị loại khỏi tập held-out. So sánh giữa các cấu hình vẫn công bằng vì dùng chung một tập.

Hạn chế và hướng phát triển

Hạn chế

  • Thực nghiệm nhỏ: Python 1 lượt (đề yêu cầu 3), JS/TS chưa có A/B/C/D, 1 model, 9 module tự viết
  • Ngưỡng mutation 80 % làm vòng lặp dừng sớm
  • LLM có thể phân loại sai, test có thể bám chi tiết cài đặt
  • Phụ thuộc đặc tả: không có docstring hoặc JSDoc thì không có căn cứ so sánh
  • Công cụ đo khác nhau nên so sánh giữa hai ngôn ngữ chỉ tương đối

Hướng phát triển

  • Chạy đủ 3 lượt cho mỗi ngôn ngữ, với ngưỡng mutation cao hơn
  • Thử trên HumanEval để so sánh trực tiếp với số liệu của MuTAP
  • Thử cách của Zhao và cộng sự: thay code trong prompt bằng đặc tả để giảm dẫn dắt sai
  • Thêm Java, Go; Java đã phác thảo với JUnit 5, JaCoCo, PIT
  • Thêm bước rút gọn bộ test như MuTAP

Kết luận

Đã xây dựng: agent sinh, chạy, đo, sửa và bổ sung test cho Python và JavaScript/TypeScript, kế thừa ý tưởng phản hồi mutation của MuTAP.

Hai đóng góp so với MuTAP

  • Không mặc định code đúng: khi test fail thì so với đặc tả, giữ lại test phát hiện bug thay vì sửa cho khớp code
  • Chấm trên mutant LLM chưa thấy: cho thấy cách chấm có thể làm đổi kết luận (tăng 3 điểm so với không tăng)

Với số liệu hiện có

  • Lợi ích rõ nhất là xử lý test fail: 1,2 xuống 0 mỗi module, gắn nhãn đúng 2/2 bug Python
  • Lợi ích của phản hồi mutation trên lỗi mới chưa được xác nhận
  • Con người vẫn là người xác nhận cuối cùng
Em xin cảm ơn thầy/cô đã lắng nghe và xin nhận câu hỏi.
